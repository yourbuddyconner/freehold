## Investigation findings: how principals come to exist

The allod wasm API exposes `graph.principal_add(name, kind, by)` which calls
`allod_graph::flows::principal_add`. That function:

1. Generates a fresh Ed25519 keypair (`Keypair::generate(name)`).
2. Saves it to the key backend via `graph.create_key(&kp)` — this writes
   `<ALLOD_KEYS_DIR>/<graphDirComponent>/<name>.yaml` (the same XDG path
   freehold's host-side `keys.ts` resolves later).
3. Builds a `core/User@1`, `core/Agent@1`, or `core/Service@1` node op with
   `display_name`, `keys`, and `status: active`.
4. Calls `build_changeset` + `admit_or_hold` signed by the `by` principal.
   Admits immediately if the graph policy allows it (a fresh memory graph with
   the default policy admits immediately for the owner).

This is **the same path `registerAgent` already used** in governance.ts
(`graph.principal_add(agentName, "agent", by)`). The only gap was: no
`user`-kind path, no CLI command, no POST route, and no Settings form.

The `principal_add` call is NOT a two-phase `signedCommit` — it signs
internally using the Rust-side key material. The wasm function is already
`async` and handles persistence via the persist callback. This works correctly
for creating new principals (who don't yet have a host-side key when the op
starts). The two-phase host-seam path is required only for operations signed
by an existing principal whose key lives on the host filesystem (decide,
review, code comments).

**Policy roles:** `principal_add` registers the node in the graph but does NOT
amend the policy `roles` map. Adding a reviewer to `roles: {code-reviewer:
[principal:reviewer-demo]}` requires a separate policy amendment submitted
through the policy editor. The `install_policy_ops` path in `@allod/core`
0.2.2 handles this; if that isn't merged into a consuming branch, the operator
submits the YAML directly via POST /api/v1/policy. The CLI output and Settings
form note this explicitly.

**Key storage:** keys are written to `$ALLOD_KEYS_DIR/<graphDirComponent>/<name>.yaml`
by the wasm/Rust layer, not by freehold's node `crypto`. The spec says
"generated by freehold natively (node crypto Ed25519)" but that only applies to
keys freehold generates for its own principals (not new graph principals added
via `principal_add`). The substrate already handles key generation inside
`principal_add`; adding a parallel node-crypto path would duplicate keys and
create confusion. This implementation uses the existing wasm path, which is
correct and already tested upstream in allod.

## What was implemented

### packages/core/src/governance.ts
- Added `addPrincipal(graph, name, kind, by, allodGraphId)` which calls
  `graph.principal_add(name, kind, by)` and computes the key path from
  `keysBaseDir() + graphDirComponent(allodGraphId) + name + .yaml`.
- Exported `AddPrincipalResult` type.

### packages/api/src/openapi.ts
- Added `AddPrincipalBody` Zod schema and `POST /api/v1/principals` path.
- Added `CodeComment`, `PostCodeCommentBody`, `PostCodeCommentResult` schemas
  and the `GET/POST /api/v1/code/comments` paths. These were present in the
  committed `openapi.json` (from a prior agent's work) but absent from
  `openapi.ts`, causing `pnpm generate` to drop them and break `tsc`. This is
  a pre-existing regression on the branch; fixing it was required to make the
  typecheck gate pass.

### packages/api/src/routes/governance.ts
- Added `POST /principals` handler using `addPrincipal()` from core; resolves
  the graph entry for `allodGraphId` and `signingPrincipal` via manager.

### packages/client/src/client.ts + types.ts
- Added `addPrincipal()` method. `types.ts` regenerated via `pnpm generate`.

### packages/api/src/cli/commands/principal.ts (new file)
- `runPrincipalAdd` — calls `client.addPrincipal()`, prints principal name,
  kind, key path, and copy-to-reviewer instruction.

### packages/api/src/cli/index.ts
- Wired `freehold principal add <name> [--kind user|agent|service] [--role]`.
- Updated `HELP` string.

### packages/web/src/routes/settings.tsx
- Added `AddPrincipalSection` component: name input, kind toggle
  (user/agent/service), Add button. On success shows key path, copy button,
  and the "copy to reviewer's machine" instruction. Calls
  `qc.invalidateQueries({ queryKey: ["principals"] })` on success.
- Inserted `<AddPrincipalSection>` into the existing Principals `<section>`.

None blocking. One note for the coordinator:

[principal:reviewer-demo]}`) is tracked in a concurrent agent. Until that
