MCP Tools

Agents connect over streamable HTTP MCP at /mcp and get exactly these thirteen tools. Agents can propose schema and policy changes, but there are no tools for approving, rejecting, or touching keys; every governed change waits for your decision. Every write tool returns either { status: "saved", changeset } or { status: "pending", proposal, rule }.

A write that comes back pending is stored as a proposal. The response includes the proposal and the rule that matched, and the agent can look it up later with pending_approvals. See Governance for how proposals are decided.

Knowledge tools

These tools write to the graph. Each write is an atomic changeset. Quick scratch notes save instantly; writes the policy rules cover become pending proposals.

remember saves instantly

The fast path for capturing a thought. Creates a memory/Note entity classified as scratch and saves it instantly. This is sugar over create_entity and does not accept type overrides or relationships.

Parameters
  • content (string, required) — the text of the note
  • agent (string, optional) — agent principal name; defaults to the configured agent
Approval: None needed. The note saves instantly under the scratch-is-free rule and is retrievable via recall right away.
create_entity may need approval

Create a typed entity with optional classifications and edges in one atomic changeset. The entity type can be any type installed in the graph's schema. Creating a memory/Preference, or anything else the policy rules cover, is the most common way to end up with a pending write.

Parameters
  • type (string, required) — a type ref from the installed schema, e.g. memory/Preference@1
  • attributes (object, required) — key/value pairs matching the type's schema
  • classify (string, optional) — a taxonomy term to apply in the same changeset, e.g. workspace/scratch@1
  • relate (object, optional) — an edge to create after the entity: { to, edge_type, attributes? }. The edge is a second changeset; if the entity write is pending, the edge is skipped.
  • agent (string, optional) — agent principal name
Approval: Depends on policy. Scratch-classified entities save instantly; preferences, people, and agreements wait for your approval.
update_entity may need approval

Revise an existing entity's attributes. The server reads the entity's current revision and pins the update against it (optimistic concurrency), so conflicting updates cannot silently overwrite each other.

Parameters
  • id (string, required) — the entity's identifier (bare UUID)
  • type (string, required) — the entity's type ref, required for validation
  • attributes (object, required) — attributes to update
  • agent (string, optional) — agent principal name
Approval: Follows the same policy as the entity's type. An entity that needed your approval to create needs it to change.
relate may need approval

Create a typed edge between two existing nodes. Edge types declare a valid domain and range, and the graph rejects edges that violate them. Time-bounded relationships carry from and until attributes on the edge.

Parameters
  • from (string, required) — source node identifier (bare UUID)
  • to (string, required) — target node identifier (bare UUID)
  • edge_type (string, required) — an edge type ref, e.g. memory/relates_to@1
  • attributes (object, optional) — edge attributes
  • scratch (boolean, optional, default true) — classify the edge as scratch so it saves instantly; pass false to send it through the policy rules
  • agent (string, optional) — agent principal name
Approval: Saves instantly by default (scratch). With scratch: false, the policy rules decide.
classify may need approval

Place a node in the taxonomy. Classification decides which policy rules apply: the terms on an object determine what its changes must satisfy. Because of that, a classification write can itself need approval.

Parameters
  • subject (string, required) — the node to classify (bare UUID)
  • term (string, required) — the taxonomy term, e.g. life/health@1
  • agent (string, optional) — agent principal name
Approval: Depends on the taxonomy term and the target object's type. Classifying something under a governed term can require your approval.
attach_document usually instant

Anchor source material in the graph by content hash. The document is addressed by the SHA-256 of its bytes, so claims can cite an exact, checkable source. In v0 the document is associated with an entity through the changeset's intent text; edges cannot target document-kind objects.

Parameters
  • entity_id (string, required) — the entity this document supports (bare UUID)
  • content (string, required) — the document text to anchor
  • media_type (string, optional) — MIME type, e.g. text/markdown; defaults to text/plain
  • title (string, optional) — a document title
  • agent (string, optional) — agent principal name
Approval: None needed — documents save under the scratch rule. The response includes the document's content hash.

Retrieval tools

Read-only. These tools do not create changesets and never need approval.

recall read-only

Hybrid search: pgvector cosine similarity (bge-small-en-v1.5, 384 dimensions) merged with Postgres full-text search over the PGlite index. Every result says who wrote it, who approved it, and which changeset it came from. The embedding model runs in-process via transformers.js, so memory never leaves the machine.

Parameters
  • query (string, required) — natural-language search query
  • filters (object, optional):
    • type — restrict to an entity type ref
    • author — restrict to an author principal name
    • approval — restrict by approval status (saved/pending)
  • limit (number, optional) — maximum results, default 10
Note: The compiled binary ships the hash embedder only, so semantic similarity is unavailable there and search relies on full-text matching. Run from source for full hybrid recall.
get_entity read-only

Retrieve one object in full: its current attributes, classifications, all typed edges (with their edge types, direction, and attributes), the full history of who wrote and approved it, and its revision history.

Parameters
  • id (string, required) — the entity's stable identifier
traverse read-only

Walk the typed graph from a starting node, following edges of specified types in either direction, up to a maximum depth. This answers questions like "what does this preference derive from?".

Parameters
  • from (string, required) — starting node identifier (bare UUID)
  • edge_types (string[], optional) — restrict traversal to these edge types; omit to follow all edges
  • direction (string, optional) — out (default), in, or both
  • depth (number, optional) — maximum hops, default 1, maximum 10
pending_approvals read-only

Return the agent's own pending writes: proposals submitted but not yet decided. An agent uses this to check on a previous write before retrying or proceeding.

Parameters
  • None. The result is scoped to the calling agent's identity.

Schema tools

These tools let agents read and extend the graph's schema. Schema changes go through the same approval flow as knowledge writes — they always wait for your decision.

describe_schema read-only

Return the graph's installed ontologies as structured data. An agent calls this to learn what the graph can hold before creating an entity or proposing a new type. The answer comes from the graph itself, so what the agent sees is what is actually installed.

Returns
  • Entity types with attribute schemas (name, type expression, required flag) and inheritance
  • Edge types with domain, range, and cardinality
  • The taxonomy terms with their parents
propose_ontology_change needs approval

Propose a change to the graph's installed schema: new entity types, edge types, or taxonomy terms, written as an ontology package in YAML. The proposal is created under the schema-changes-are-serious rule, appears in your inbox alongside knowledge proposals, and is installed when you approve it.

Parameters
  • package_name (string, required) — the ontology package name, e.g. my-workspace
  • ontology_yaml (string, required) — the package in Allod projection form: ontology, version, entity_types, edge_types, and so on
  • agent (string, optional) — agent principal name
Approval: Always required. A schema change is an ordinary in-graph changeset: the proposal creates meta/EntityType and related nodes, signed and carrying provenance like every other write.
propose_policy_change needs approval

Propose a replacement policy for the graph. The submitted document replaces the whole policy — default posture, roles, and every rule — so an agent reads the current policy first, modifies it, and submits the complete result. The proposal waits in your inbox and the active policy is unchanged until you approve it. The Policy page in the console shows the same rules in plain language, and your own edits there travel this same path.

Parameters
  • policy_yaml (string, required) — the complete policy document, YAML or JSON
  • rationale (string, optional) — one or two sentences on why the change is worth your attention
  • agent (string, optional) — agent principal name
Approval: Always required. The set-policy operation is itself governed, so even a proposal to loosen the rules is decided under the rules that exist now.
