MCP Tools

Agents connect over streamable HTTP MCP at /mcp. The tool surface is a strict subset of the HTTP API: agents never get approval, rejection, policy mutation, or key operations through the tool surface. Every write tool returns either { status: "admitted", changeset } or { status: "held", proposal, rule }.

A held response is a first-class success shape, not an error. The agent received a valid response; the write is in the queue. See Governance for how held writes are reviewed and admitted.

Knowledge tools

These tools write to the graph. Each write is an atomic changeset. Scratch-classified writes are admitted immediately; governed writes are held by policy.

remember admitted immediately

The ergonomic fast path for capturing a thought or observation. Creates a memory/Note entity classified as scratch and admits it immediately. This is sugar over create_entity — it does not accept type overrides or relationship parameters.

Parameters
  • content (string, required) — the text of the note
Admission: Always admitted. Scratch notes bypass the policy engine. The note is immediately indexed and retrievable via recall.
create_entity may be held

Create a typed node with optional classifications and edges in one atomic changeset. The entity type is any type installed in the graph's schema — not a fixed menu. The most common path to a held write: creating a memory/Preference or any entity that policy routes as consequential.

Parameters
  • type (string, required) — a fully-qualified type name from the installed schema, e.g., memory/Preference, core/Person
  • attributes (object, required) — attribute key-value pairs matching the type's schema
  • classify (string[], optional) — taxonomy terms to apply in the same changeset
  • relate (object[], optional) — edges to create in the same changeset: { to, edge_type, attributes? }
Admission: Depends on policy. Entities classified as scratch are admitted; governed types (preferences, people, agreements) are held pending owner approval.
update_entity may be held

Revise an existing entity's attributes. Uses optimistic concurrency: the request includes the entity's current revision identifier, and the server rejects the update if the entity has been modified since. This prevents conflicting updates from silently overwriting each other.

Parameters
  • id (string, required) — the entity's stable identifier
  • attributes (object, required) — attribute fields to set; unspecified fields are unchanged
  • revision (string, required) — the entity's current revision, returned by get_entity
Admission: Follows the same policy as the entity's type. Updates to governed entities are held.
relate may be held

Create a typed edge between two existing nodes. Edge types define the valid domain and range (e.g., a derived_from edge must connect a knowledge entity to its source). Time lives on edges — use from and until attributes following the corp-ontology convention for time-bounded relationships.

Parameters
  • from (string, required) — source entity identifier
  • to (string, required) — target entity identifier
  • edge_type (string, required) — a fully-qualified edge type from the installed schema
  • attributes (object, optional) — edge attributes, including from/until timestamps
Admission: Policy-dependent. Edges connecting governed entities are typically held.
classify may be held

Place a node, edge, or document in the taxonomy. Classification affects policy routing — classifying a node under a governed taxonomy term can change which policy rules apply to it. For this reason, classification can itself be held.

Parameters
  • subject (string, required) — the identifier of the node, edge, or document to classify
  • term (string, required) — the taxonomy term to apply, e.g., life/health, work/project
Admission: Depends on the taxonomy term and the target object's type. Classification under a governed term may be held.
attach_document typically admitted

Anchor source material in the graph by content hash. The document is stored and addressed by the hash of its content — other entities can cite exact bytes by referencing the hash. Use this to give claims a durable source reference.

Parameters
  • content (string, required) — the document text to anchor
  • media_type (string, required) — MIME type, e.g., text/plain, text/markdown
Admission: Documents in the scratch region are admitted immediately. The content hash is returned for use in subsequent relate calls.

Retrieval tools

Read-only. These tools do not create changesets and are never held by policy.

recall read-only

Hybrid search: pgvector cosine similarity (bge-small-en-v1.5, 384-dim) merged with Postgres full-text search, over the PGlite index. Every result carries its provenance: changeset hash, author DID, approval status, and the rule (if any) that governed the write. Memory never leaves the machine — the embedding model runs in-process via transformers.js.

Parameters
  • query (string, required) — natural language search query
  • filters (object, optional):
    • type — restrict to a specific entity type
    • region — restrict to a graph region (e.g., scratch, governed)
    • author — restrict to a specific author DID
    • approval_status — one of admitted, held, rejected
Note: When running from the compiled binary, semantic (cosine similarity) recall is unavailable and the search falls back to BM25 full-text + hash vectors. Run from source for full hybrid recall.
get_entity read-only

Retrieve one object in full: its current attributes, classifications, all typed edges (with their edge types, direction, and attributes), the full provenance chain (who wrote it, who approved it, the changeset hash), and revision history.

Parameters
  • id (string, required) — the entity's stable identifier
traverse read-only

Walk the typed graph from a starting node. Follow specific edge types in either direction (outbound, inbound, or both) up to a configurable depth. Useful for answering questions like "what does this preference derive from?" or "who else relates to this document?"

Parameters
  • from (string, required) — starting entity identifier
  • edge_types (string[], optional) — restrict traversal to these edge types; if omitted, follows all edges
  • direction (string, optional) — outbound (default), inbound, or both
  • depth (number, optional) — maximum traversal depth, default 2
pending_approvals read-only

Return the agent's own held proposals — writes that have been submitted but not yet approved or rejected by the owner. The agent can use this to check whether a previous write is still pending, approved, or rejected before deciding to re-attempt or proceed.

Parameters
  • None. The result is scoped to the calling agent's identity.

Schema tools

These tools let agents read and evolve the graph's ontology. Schema changes follow the same governance lifecycle as knowledge writes — they are always held and require owner approval.

describe_schema read-only

Return the graph's installed ontologies as structured data. An agent calls this to learn what types the graph currently holds before deciding whether to create an entity or propose a new type. The schema is read from the graph itself — not from documentation — so what the agent sees is what is actually installed.

Returns
  • Entity types with attribute schemas (name, type expression, required flag) and inheritance chains
  • Edge types with domain, range, cardinality, and attributes
  • The full taxonomy tree
  • Installed package versions and import hashes
Design note: This is how an agent learns what the graph can hold — not from documentation, but from the graph itself. It is the entry point to the schema loop.
propose_ontology_change always held

Propose a change to the graph's installed schema: add an entity type, add an edge type, or add a taxonomy term. Schema proposals are always held — the schema-changes-are-serious policy rule applies unconditionally. The proposal appears in the owner's Inbox alongside knowledge proposals, reviewed and installed on approval. This is the agent's path to evolving its world-model under governance.

Parameters
  • change (object, required):
    • kind — add_entity_type, add_edge_type, or add_taxonomy_term
    • name — the proposed type or term name
    • extends (for entity types) — parent type, e.g., core/Person
    • attributes (for entity types) — array of { name, type, required }
    • domain / range (for edge types)
    • parent (for taxonomy terms)
Admission: Always held. Schema changes are in-graph changesets — a proposed entity type is a held changeset that creates a meta/EntityType node, governed, signed, and provenance-carrying like every other write.
