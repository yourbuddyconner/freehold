MCP Tools

Agents connect over streamable HTTP MCP at /mcp and get exactly these twelve tools. There are no tools for approving, rejecting, changing policy, or touching keys; those operations exist only in the owner's API. Every write tool returns either { status: "admitted", changeset } or { status: "held", proposal, rule }.

A held response is a success shape, not an error. The agent received a valid response, and the write is queued for review. See Governance for how held writes are reviewed and admitted.

Knowledge tools

These tools write to the graph. Each write is an atomic changeset. Scratch writes are admitted immediately, and governed writes are held by policy.

remember admitted immediately

The fast path for capturing a thought. Creates a memory/Note entity classified as scratch and admits it immediately. This is sugar over create_entity and does not accept type overrides or relationships.

Parameters
  • content (string, required) — the text of the note
  • agent (string, optional) — agent principal name; defaults to the configured agent
Admission: Admitted immediately under the scratch-is-free policy rule. The note is indexed and retrievable via recall.
create_entity may be held

Create a typed node with optional classifications and edges in one atomic changeset. The entity type can be any type installed in the graph's schema. Creating a memory/Preference, or any other entity the policy treats as consequential, is the most common way to produce a held write.

Parameters
  • type (string, required) — a type ref from the installed schema, e.g. memory/Preference@1
  • attributes (object, required) — key/value pairs matching the type's schema
  • classify (string, optional) — a taxonomy term to apply in the same changeset, e.g. workspace/scratch@1
  • relate (object, optional) — an edge to create after the entity: { to, edge_type, attributes? }. The edge is a second changeset; if the entity is held, the edge is skipped.
  • agent (string, optional) — agent principal name
Admission: Depends on policy. Entities classified as scratch are admitted; governed types (preferences, people, agreements) are held pending owner approval.
update_entity may be held

Revise an existing entity's attributes. The server reads the entity's current revision and pins the update against it (optimistic concurrency), so conflicting updates cannot silently overwrite each other.

Parameters
  • id (string, required) — the entity's identifier (bare UUID)
  • type (string, required) — the entity's type ref, required for validation
  • attributes (object, required) — attributes to update
  • agent (string, optional) — agent principal name
Admission: Follows the same policy as the entity's type. Updates to governed entities are held.
relate may be held

Create a typed edge between two existing nodes. Edge types declare a valid domain and range, and the graph rejects edges that violate them. Time-bounded relationships carry from and until attributes on the edge.

Parameters
  • from (string, required) — source node identifier (bare UUID)
  • to (string, required) — target node identifier (bare UUID)
  • edge_type (string, required) — an edge type ref, e.g. memory/relates_to@1
  • attributes (object, optional) — edge attributes
  • scratch (boolean, optional, default true) — classify the edge as scratch so it admits immediately; pass false to route it through governance
  • agent (string, optional) — agent principal name
Admission: Admitted immediately by default (scratch). With scratch: false, policy decides.
classify may be held

Place a node in the taxonomy. Classification routes policy: the terms on an object decide which rules apply to changes of it. For that reason a classification write can itself be held.

Parameters
  • subject (string, required) — the node to classify (bare UUID)
  • term (string, required) — the taxonomy term, e.g. life/health@1
  • agent (string, optional) — agent principal name
Admission: Depends on the taxonomy term and the target object's type. Classification under a governed term may be held.
attach_document typically admitted

Anchor source material in the graph by content hash. The document is addressed by the SHA-256 of its bytes, so claims can cite an exact, checkable source. In v0 the document is associated with an entity through the changeset's intent text; edges cannot target document-kind objects.

Parameters
  • entity_id (string, required) — the entity this document supports (bare UUID)
  • content (string, required) — the document text to anchor
  • media_type (string, optional) — MIME type, e.g. text/markdown; defaults to text/plain
  • title (string, optional) — a document title
  • agent (string, optional) — agent principal name
Admission: Admitted under the scratch rule. The response includes the document's content hash.

Retrieval tools

Read-only. These tools do not create changesets and are never held by policy.

recall read-only

Hybrid search: pgvector cosine similarity (bge-small-en-v1.5, 384 dimensions) merged with Postgres full-text search over the PGlite index. Every result carries its provenance: changeset hash, author principal, method, and approval status. The embedding model runs in-process via transformers.js, so memory never leaves the machine.

Parameters
  • query (string, required) — natural-language search query
  • filters (object, optional):
    • type — restrict to an entity type ref
    • author — restrict to an author principal name
    • approval — restrict by approval status
  • limit (number, optional) — maximum results, default 10
Note: The compiled binary ships the hash embedder only, so semantic similarity is unavailable there and search relies on full-text matching. Run from source for full hybrid recall.
get_entity read-only

Retrieve one object in full: its current attributes, classifications, all typed edges (with their edge types, direction, and attributes), the full provenance chain (who wrote it, who approved it, the changeset hash), and revision history.

Parameters
  • id (string, required) — the entity's stable identifier
traverse read-only

Walk the typed graph from a starting node, following edges of specified types in either direction, up to a maximum depth. This answers questions like "what does this preference derive from?".

Parameters
  • from (string, required) — starting node identifier (bare UUID)
  • edge_types (string[], optional) — restrict traversal to these edge types; omit to follow all edges
  • direction (string, optional) — out (default), in, or both
  • depth (number, optional) — maximum hops, default 1, maximum 10
pending_approvals read-only

Return the agent's own held proposals: writes submitted but not yet decided by the owner. An agent uses this to check on a previous write before retrying or proceeding.

Parameters
  • None. The result is scoped to the calling agent's identity.

Schema tools

These tools let agents read and evolve the graph's ontology. Schema changes follow the same governance lifecycle as knowledge writes — they are always held and require owner approval.

describe_schema read-only

Return the graph's installed ontologies as structured data. An agent calls this to learn what the graph can hold before creating an entity or proposing a new type. The answer comes from the graph itself, so what the agent sees is what is actually installed.

Returns
  • Entity types with attribute schemas (name, type expression, required flag) and inheritance
  • Edge types with domain, range, and cardinality
  • The taxonomy terms with their parents
propose_ontology_change always held

Propose a change to the graph's installed schema: new entity types, edge types, or taxonomy terms, written as an ontology package in YAML. The proposal is held under the schema-changes-are-serious rule, appears in the owner's Inbox alongside knowledge proposals, and is installed on approval.

Parameters
  • package_name (string, required) — the ontology package name, e.g. my-workspace
  • ontology_yaml (string, required) — the package in Allod projection form: ontology, version, entity_types, edge_types, and so on
  • agent (string, optional) — agent principal name
Admission: Always held. A schema change is an ordinary in-graph changeset: the proposal creates meta/EntityType and related nodes, signed and provenance-carrying like every other write.
