Architecture

The system has three actors: your agents, you, and a verifier anyone can run. The daemon sits between the first two, and everything the actors do ends up as signed entries in one log on your disk.

The system

  • Your agents connect over MCP and write memory. Every write is signed with that agent's own key.
  • You use the console and the CLI. Pending proposals come to your inbox, and your approvals and rejections are signed with the owner key.
  • The daemon runs the policy rules and appends every saved write and every decision to the graph, in order.
  • The graph is the append-only log on your disk. It is the system's only source of truth.
  • The search index is derived from the graph and can be thrown away and rebuilt at any time.
  • The verifier is a separate program that reads the graph files directly and checks the whole history.

How signatures work

Three mechanisms make the history checkable:

  • Agent signatures. When an agent is registered, it gets its own keypair. Every changeset the agent writes is signed with that key, so each memory traces to the agent that wrote it.
  • Your signature. The owner key is created at first boot and stays in ~/.freehold. Approvals and rejections are decision records signed with it. A preference about you is only true if your signature says so.
  • The hash chain. Each changeset names the hash of the one before it. Changing any entry breaks the hash of every entry after it, so history cannot be quietly rewritten.

All three are properties of the files themselves, so checking them requires no trust in Freehold — see independent verification.

The graph

Memory is a typed graph: entities, relationships between them, and the schema that defines both. It is stored as an append-only log of changesets on your disk. Nothing is edited in place and nothing is deleted; the current state of memory is the result of replaying the log from the beginning.

The format is Allod, a separate open project. Your graph is readable and verifiable without Freehold, and the schema itself lives inside the graph as ordinary entries — which is why agents can propose schema changes through the same approval flow as everything else.

The path of a write

  1. An agent calls a tool, such as remember or create_entity.
  2. The daemon builds a changeset signed with the agent's key.
  3. The policy rules match it: notes save immediately, and writes the rules name become pending proposals in your inbox.
  4. You approve or reject. The decision record is signed with your key and appended to the log.
  5. Saved objects are added to the search index, with an embedding computed on your machine.
  6. recall returns them with their author, approval status, and changeset hash.

The search index

The index exists so recall is fast: an embedded database with vector and full-text search over everything saved. Embeddings are computed locally, so memory never leaves the machine.

The index carries nothing the log cannot reproduce. You can delete it at any time and freehold reindex rebuilds it from the log, landing on identical state. The log is the only thing you need to protect.

Independent verification

Verification checks three things, one per signature mechanism:

  • Integrity. Every changeset's hash matches the reference in the entry after it. Tampering anywhere breaks the chain.
  • Authorship. Every signature verifies against its author's registered public key.
  • Governance. Every write that needed approval has a matching decision record signed with your key.

The Rust allod verify command performs all three from the files alone: run allod verify ~/.freehold/graphs/main with no daemon running and you get the same pass/fail result as the console's Verify page. You never have to trust Freehold's own verification code.

Design choices

One binary, server and client

freehold serve runs the full product: the agent API, the MCP endpoint, and the console on one local port. Every other command — pending, approve, recall, verify, and the rest — is a client of the running daemon through the same public API the console uses. There is no side door into the engine.

Local only

The daemon binds 127.0.0.1 and mints a bearer token into ~/.freehold/config.json (mode 0600) at first boot. The CLI, the console, and agent MCP configs use that token. Multi-user and remote deployments are out of scope for v0.

MCP over HTTP

Agents connect to the running daemon at /mcp; there is no stdio transport, so the daemon must be up for agents to reach memory. freehold mcp setup claude-code writes the config entry that points an agent at it.

Disk layout

~/.freehold/
  config.json          # bearer token, graph name, embedder choice
  pg/                  # the search index (delete freely; reindex rebuilds it)
  graphs/
    main/              # your graph, in the open Allod format
      .allod/
        graph.yaml     # graph ID, root authority
        HEAD           # tip changeset hash
        changesets/    # the append-only log, one file per changeset
        proposals/     # pending writes awaiting your decision
        keys/          # your key and each agent's key
        checkpoints/   # signed checkpoints

The graphs/main/ directory is what allod verify reads and what you back up. Everything else can be regenerated.
