Architecture

Freehold runs as a single daemon on your machine. Your agents connect to it over MCP, you connect to it through the console and the CLI, and everything in between — the policy check, the signed log, the search index — lives in that one process and on your disk.

The system

your agents ── MCP ──────┐        ┌────── console + CLI ── you
                         ▼        ▼
              freehold daemon (127.0.0.1:8710)
                         │
        policy check: save instantly, or mark pending for you
                         │
                         ▼
        append-only signed log     ~/.freehold/graphs/main
                         │
                         ▼  derived
        search index (embedded Postgres)   rebuilt any time from the log
  • The daemon (freehold serve) listens on one local port and serves three things from it: the MCP endpoint agents connect to, the HTTP API, and your console.
  • The graph is your memory: an append-only log of signed changesets on disk, in the open Allod format. Nothing is edited in place or deleted; the current state is the result of replaying the log.
  • The policy engine checks every write against the rules declared in the graph. Quick notes save instantly; anything the rules cover becomes a pending proposal for you to approve or reject.
  • The search index is an embedded Postgres (PGlite) with vector embeddings, built from the log. recall queries it. It holds nothing the log cannot reproduce.
  • The console and the CLI are clients of the daemon's HTTP API. Approving, rejecting, policy edits, and verification live here — agents never get those.

The Allod foundation

Freehold's storage is built on Allod — an append-only log of signed changesets with a typed object model. Allod is a separate project. Freehold consumes @allod/core, the WASM npm package produced from the Allod Rust codebase.

The key properties Freehold inherits from Allod:

  • Append-only log. Changesets are never deleted or modified. The current state is the result of replaying the log.
  • Signed changesets. Every changeset is signed by the author's key. Authorship can be verified without trusting any intermediary.
  • Typed object model. Objects have types defined in a schema that lives in the graph itself. The schema is versioned and import-hashed.
  • Native on-disk layout. Graphs are stored in Allod's native format — the Rust allod CLI can open any graph Freehold writes without modification.
  • Schema as objects. A proposed entity type is a real in-graph changeset that creates meta/EntityType nodes. There is no side-channel schema store.

Because Freehold stores graphs in native Allod format, anything Freehold writes can be opened and verified by the Rust allod CLI, with no Freehold code involved.

The path of a write

From an agent write to a searchable, verified record:

  1. An agent calls an MCP tool or the HTTP API directly.
  2. The daemon validates the request against its published OpenAPI schema.
  3. The daemon builds a signed Allod changeset from the request.
  4. The policy engine matches the changeset against the installed rules. Quick notes save immediately; anything the rules cover becomes a pending proposal.
  5. Once the write is saved (immediately or after your approval), the new objects are folded into the search index: one row per object plus a locally-computed embedding (bge-small-en-v1.5 via transformers.js WASM ONNX).
  6. Retrieval via recall runs a vector similarity query merged with full-text search. Every result says who wrote it and who approved it.

Disposable index

The search index carries nothing the log cannot reproduce. Embeddings are derived data, computed locally from the content itself. You can wipe the index at any time and freehold reindex rebuilds it from the log, landing on identical state.

This is also the recovery path: if the index directory is lost or corrupted, freehold reindex brings it back. The log is the only thing you need to protect.

Verification independence

Freehold's verification surface is three levels:

  • Integrity. Hash chain verification — each changeset's content hash matches its predecessor's reference. Tampering with any changeset breaks the chain.
  • Authorship. Signature verification — each changeset's signature verifies against the author's registered public key.
  • Governance. Decision record verification — every write that needed approval has a corresponding decision record signed with your key.

Verification does not depend on Freehold. The Rust allod verify command performs all three levels independently: run allod verify ~/.freehold/graphs/main with no daemon running and you get the same pass/fail result as the console's Verify page. You never have to trust Freehold's own verification code.

Key decisions

One binary, server and client

freehold serve boots the full product: HTTP API, MCP endpoint, and the console on one local port. Every other subcommand (status, pending, approve, reject, remember, recall, verify, reindex, mcp setup) is a client of a running instance through the public HTTP API. There is no side door into the engine.

Because the CLI goes through the same public API as everything else, there is no hidden behavior the API cannot express, and only one process ever touches the database.

No native modules

No native .node modules anywhere in the dependency tree. PGlite (embedded Postgres) is WASM. @allod/core is WASM. Embeddings run via transformers.js (WASM ONNX), not fastembed or any native binding. This discipline is what makes the single compiled binary possible.

MCP over HTTP, no stdio bridge

The daemon serves streamable-HTTP MCP at /mcp. There is no stdio MCP transport. Agent connections require the daemon to be running and reachable at the configured address. freehold mcp setup claude-code writes the MCP config entry pointing at the running daemon.

Local-first auth

The daemon binds 127.0.0.1. A bearer token is auto-minted into ~/.freehold/config.json (mode 0600) at first boot. The CLI, the console, and MCP configs use this token. Multi-user and remote deployments are out of scope for v0.

Disk layout

~/.freehold/
  config.json          # bearer token, graph name, embedder choice
  pg/                  # PGlite data directory (single owner: the daemon)
  graphs/
    main/              # native Allod layout
      .allod/
        graph.yaml     # graph ID, root authority
        HEAD           # tip changeset hash
        changesets/    # the append-only log, one file per changeset
        proposals/     # pending writes awaiting your decision
        keys/          # keypairs (plain-keypair profile)
        checkpoints/   # signed checkpoints

The graphs/main/ directory is native Allod format. The Rust allod CLI opens it directly. The schema is not a directory: since Allod's schema materialization, ontology types and policy live in the graph as meta-typed nodes, created by the genesis changeset.
