Architecture

Freehold is one daemon built from four packages in a pnpm workspace. The graph storage, policy engine, recall index, and agent API are separate concerns with clear ownership. No native modules anywhere in the tree — the single binary is possible because every moving part is WASM or pure JavaScript.

Package structure

Package Role
packages/core The only package that touches Allod. Wraps @allod/core, owns PGlite, and exposes typed operations matching the product surface: the knowledge ops, retrieval, schema, and governance. Nothing above this layer sees Allod primitives directly.
packages/api The daemon and the CLI in one artifact. Hono routes defined schema-first with @hono/zod-openapi — the routes generate openapi.json. The /mcp endpoint serves streamable HTTP MCP. Static serving of the console with SPA fallback. All CLI subcommands are clients of the running daemon through the public HTTP API only.
packages/client Generated from openapi.json by openapi-typescript in CI. Never hand-edited. The build fails if it drifts from the spec. Used by the CLI, the console, and any future integration equally — the same public-API conformance rule everywhere.
packages/web The owner console: React 19, TanStack Router with colocated route tests, TanStack Query for server state. Tailwind + Radix primitives. Consumes packages/client only — never imports from packages/core or packages/api directly.

The Allod foundation

Freehold's storage is built on Allod — an append-only log of signed changesets with a typed object model. Allod is a separate project and codebase. Freehold consumes @allod/core, the WASM npm package produced from the Allod Rust codebase.

The key properties Freehold inherits from Allod:

  • Append-only log. Changesets are never deleted or modified. The graph's history is its truth.
  • Signed changesets. Every changeset is signed by the author's key. Authorship can be verified without trusting any intermediary.
  • Typed object model. Objects have types defined in a schema that lives in the graph itself. The schema is versioned and import-hashed.
  • Native on-disk layout. Graphs are stored in Allod's native format — the Rust allod CLI can open any graph Freehold writes without modification.
  • Schema as objects. Allod's schema materialization ships before Freehold — proposed entity types are real in-graph changesets creating meta/EntityType nodes, not a side-channel schema store.

Because Freehold stores graphs in native Allod format, cross-implementation verification is a standing conformance check in CI: the TypeScript tests write a graph, then the Rust allod verify command passes on it.

Data flow

The path from an agent write to a searchable, verified record:

  1. Agent calls an MCP tool or the HTTP API directly.
  2. packages/api validates the request against the OpenAPI schema, then calls the corresponding operation in packages/core.
  3. packages/core builds an Allod changeset and submits it to the admission layer.
  4. The admission layer runs the changeset through the policy engine. Scratch-classified writes pass immediately; governed writes are held as proposals.
  5. On admission (immediate or after owner approval), the core layer folds the new objects into PGlite: one row per object plus a locally-computed embedding (bge-small-en-v1.5 via transformers.js WASM ONNX).
  6. Retrieval via recall runs a pgvector cosine similarity query merged with Postgres full-text search. Results include provenance from the Allod graph.

Disposable index

The PGlite database carries nothing the Allod log cannot reproduce. Embeddings are derived data — they are computed from content and recomputable given the same content and model. This property is enforced by a test:

  1. Fold a set of changesets into the index
  2. Snapshot the PGlite state
  3. Wipe PGlite entirely
  4. Run freehold reindex to rebuild from the log
  5. Assert that the new state matches the snapshot

The index is also the recovery story: if the PGlite data directory is lost or corrupted, freehold reindex rebuilds it from the append-only Allod log. The log is the durable store; the index is an accelerant.

Verification independence

Freehold's verification surface is three levels:

  • Integrity. Hash chain verification — each changeset's content hash matches its predecessor's reference. Tampering with any changeset breaks the chain.
  • Authorship. Signature verification — each changeset's signature verifies against the author's registered public key.
  • Governance. Decision record verification — every governed write in the graph has a corresponding signed decision record from the owner's key.

The critical design property: verification does not depend on Freehold. The Rust allod verify command performs all three levels independently. Running allod verify ~/.freehold/graphs/memory from the terminal — with no Freehold daemon running — produces the same pass/fail result as the Freehold console's Verify page. You do not need to trust Freehold's verification implementation; you can always check with the independent implementation.

Key decisions

One binary, two personalities (the valet pattern)

freehold serve boots the full product: HTTP API, MCP endpoint, and the console on one local port. Every other subcommand (status, pending, approve, reject, remember, recall, verify, reindex, mcp setup) is a client of a running instance through the public HTTP API only — no side-door into the engine.

This design makes the CLI a permanent conformance consumer of the API. If the CLI breaks, the API is broken. It also avoids two processes sharing the PGlite database file.

No native modules

No native .node modules anywhere in the dependency tree. PGlite (embedded Postgres) is WASM. @allod/core is WASM. Embeddings run via transformers.js (WASM ONNX), not fastembed or any native binding. This discipline is what makes the single compiled binary possible.

MCP over HTTP, no stdio bridge

The daemon serves streamable-HTTP MCP at /mcp. There is no stdio MCP transport. Agent connections require the daemon to be running and reachable at the configured address. freehold mcp setup claude-code writes the MCP config entry pointing at the running daemon.

Local-first auth

The daemon binds 127.0.0.1. A bearer token is auto-minted into ~/.freehold/config.json (mode 0600) at first boot. The CLI, the console, and MCP configs use this token. Multi-user and remote deployments are out of scope for v0.

Disk layout

~/.freehold/
  config.json         # bearer token, embedding provider config
  pg/                 # PGlite data directory (single-owner discipline)
  graphs/
    memory/           # native Allod layout
      log/            # append-only changeset log
      keys/           # keypair profile (plain-keypair, per Allod spec)
      schema/         # installed ontology packages

The graphs/memory/ directory is in native Allod format and can be opened by the Rust allod CLI directly. Keys live in the graph directory, plain-keypair profile, per the Allod reference profile specification.
