Code Review

Your git repository doubles as a governed allod graph. Branch commits become review proposals, reviewer decisions are signed records stored in refs/notes/allod-decisions, and approvals travel with the repository and are verifiable without running Freehold.

Overview

When you register a git repository with Freehold, the daemon opens a second graph alongside your memory graph — a repo graph backed by the repository's own object database. The review-ontology package installs into that graph, providing the Review, ReviewComment, and ChangeRequest node types used through the review flow.

Branch heads are enumerated on each evaluation pass. For each commit, the daemon evaluates the changed paths against the graph's policy rules (via git_checklist and git_satisfaction in the wasm engine) and produces a proposal in the inbox. Reviewer decisions are signed with the reviewer's key using the same two-phase signing path used throughout Freehold — the daemon never holds a private key in memory past the signing call. Signed decision records are appended to refs/notes/allod-decisions and optionally pushed to origin immediately after the decision is written.

Setting up a repository

Register a repository from the CLI:

freehold repo add <path> [--name <n>] [--id <id>] [--principal <p>] [--no-index] [--branch <b>]

The command runs these steps in order, printing each as it runs:

  1. If <path>/.allod/graph.yaml is absent, the daemon shells to the allod binary (located via allodBin in ~/.freehold/config.json, defaulting to allod on PATH) to initialize the graph. If the binary is missing, the command stops with a plain error naming the config key.
  2. Freehold generates the principal's Ed25519 signing key if one does not already exist. Keys are written to $ALLOD_KEYS_DIR, or $XDG_DATA_HOME/allod/keys, or ~/.local/share/allod/keys — whichever is set first — under <graph-dir-component>/<principal>.yaml, mode 0600 in a 0700 directory. An existing key file is never overwritten.
  3. The repository is registered with the daemon (POST /graphs), which installs the review ontology, records the origin remote for GitHub linkage, and runs the first index pass.
  4. Unless --no-index is passed, the daemon runs allod git index <path> <branch> --as <principal> to index the default branch (default: main).
  5. The command prints a summary: graph id, principal name, key file path, and a pointer to connector setup.

The Settings → Repositories form in the console performs the same steps server-side. The daemon has filesystem access; the UI calls a POST /repos/onboard endpoint and displays each step as it completes. The graph dropdown picks up the new graph on the next page load.

The allodBin config key in ~/.freehold/config.json controls which binary is used for all shell-outs. Set it to an absolute path if allod is not on your PATH.

Review lifecycle

The evaluation pass runs when new branch heads appear. Each commit's changed paths are handed to the wasm engine alongside the graph's current policy state. The engine returns matched rule names, reviewer role requirements, and which requirements are unmet given the decision notes already written for that commit.

The inbox card shows the commit metadata, a changed-files list with per-file region tags, the matched rules, and the current checklist state. An unmet checklist means the proposal is incomplete; a satisfied checklist allows a verdict to be submitted.

Reviewing a change

Opening a proposal takes you to the review page. The left pane is a file tree of changed paths with status badges (added, modified, deleted, renamed). The right pane is a multi-file diff rendered in split view by default; a toggle switches to unified. Split/unified preference is saved at localStorage["freehold-diff-view"] and persists across reviews.

Clicking a row in the file tree scrolls to that file's diff. Clicking a line or range opens a comment composer below the selection. You write the comment body and post it; the comment becomes a draft annotation on the diff, marked pending. Drafts persist at localStorage["freehold-review-drafts:<sha>"] so a page refresh keeps them. A counter above the verdict buttons shows how many draft comments are waiting.

A comment body that starts with a suggestion fence (```suggestion) is stored as a suggested edit. Suggestion cards appear below the diff line with a Copy button and an Apply as commit button.

The verdict panel at the top of the page presents three choices:

  • Approve — approves the proposal and decides it in the same action.
  • Approve with comments — approves and attaches the drafted comments.
  • Request changes — rejects the proposal with comments.

Submitting the verdict writes the Review entity and each ReviewComment with a part_of edge, then signs and records the git decision in the same call. All writes go through the two-phase signed flow. Draft comments are cleared on submit; if the decision step fails after the comment artifacts are written, the page surfaces the error and allows a retry from the same page.

Suggestions as commits

Applying a suggestion creates a new commit directly in the object database without touching the working tree. The daemon reads the blob at the branch tip, splices the suggestion text into the affected lines, and assembles the tree and commit objects using pure git plumbing. The commit author is recorded as <reviewer> via freehold. The ref update uses an old-value guard: if the branch has moved since the suggestion was generated, the apply returns a 409 and no commit is written.

The new tip appears in the inbox as a fresh proposal. If the suggestion's content matches an earlier decided commit, the carry-forward chip shows the prior verdict — but the human decides.

Only text file suggestions on the additions side of a diff are accepted. Binary files and deletion-side spans return a 422.

Policy

Review policy rules live in the graph. Each rule selects a set of file paths (by glob or directory prefix) and declares which reviewer roles must sign off and how many are required (quorum).

An example rule in the policy editor:

- id: require-senior-for-infra
  paths:
    - "infra/**"
    - "terraform/**"
  roles:
    - senior-engineer
  quorum: 1

The wasm engine evaluates rules conjunctively: when multiple rules match a commit, all of their requirements must be satisfied. A commit that touches both infra/ and src/ must satisfy the requirements of both the infra rule and any other rule matching src/.

The Policy section of the console lists the active rules and shows which recent commits each rule matched. Editing a rule opens a YAML editor; submitting the change creates a proposal in the inbox. Policy changes are themselves proposals — the new rules take effect only after you approve the change through the same flow.

Rebases and force-pushes

When a branch is force-pushed, the daemon computes the tree hash of each new commit. If any previously decided commit has the same tree hash — meaning the file contents are identical despite a different commit SHA — the proposal card shows a chip: "same content approved as <short-sha>" with the prior verdict. The Approve button relabels "Approve again".

No automatic decisions are made. The carry-forward chip informs; the human decides. Tree hashes of prior decided commits are resolved lazily and cached with the proposal cache. If a prior commit is unreachable after the force-push, resolution fails silently and the chip is absent.

GitHub

GitHub integration connects to a repository via a Personal Access Token or a GitHub App installation. Once configured, inbound PR comments are ingested as ReviewComment nodes tagged with provenance: via github. These appear in the review page alongside comments written in Freehold, with their source noted in the annotation.

Outbound status posts happen after every decide. When the repo graph has a configured GitHub connector, the daemon posts a commit status to the origin repository: context freehold/review, state success for an approval or failure for a rejection, description naming the deciding principal. The post is fire-and-forget; if it fails, the decision is still saved locally and the decide response includes statusPosted: false with the error. A subdued notice appears in the UI on failure.

Decision records live in refs/notes/allod-decisions regardless of whether a GitHub connector is configured. The notes ref is pushed to origin on each decide (subject to the per-graph autoPushNotes setting, which defaults to on when the checkout has a remote). Push failure renders as "decision saved locally" with a retry option.

Multiple reviewers

Add a second principal with:

freehold principal add <name> [--graph <id>] [--kind user|agent|service]

This generates an Ed25519 key for the new principal and registers it in the graph. The command prints the key file path and a one-line instruction for copying it to the reviewer's machine. Remote key distribution is out of scope — the copy must happen out of band.

Role grants require a policy amendment. The policy editor in the console shows the current role assignments; adding a role for the new principal creates a policy-change proposal, which must be approved before the role takes effect. Once the role is in place, the quorum count in each matching rule is evaluated against decisions signed by principals holding that role.

The quorum evaluation is wasm-side via git_satisfaction. When the required roles and quorum are met by the decisions already recorded in the notes, the checklist shows satisfied and the proposal can be finalized.

Reference

CLI commands

Command What it does
freehold repo add <path> Register a repository: graph init, key generation, review-ontology install, first index.
freehold principal add <name> Generate a key and register a new principal in the active graph.
freehold approve <hash> Approve a pending proposal (works for git proposals and memory proposals).
freehold reject <hash> Reject a pending proposal.
freehold pending List pending proposals for the active graph.

API endpoints

Endpoint What it does
GET /git/proposals List proposals for the active repo graph: sha, ref, author, checklist, decided status.
GET /git/proposals/:sha Single proposal detail including checklist, paths, prior-decision carry-forward.
GET /git/proposals/:sha/diff Changed files with full old and new content for client-side diff rendering.
GET /git/proposals/:sha/reviews Saved Review and ReviewComment nodes for the commit, including ingested GitHub comments.
POST /git/proposals/:sha/reviews Write a verdict with optional comments. Decides the proposal in the same call when decide: true (default).
POST /git/proposals/:sha/suggestions/apply Apply a suggestion as a new git commit on the named branch.
POST /repos/onboard Server-side equivalent of freehold repo add; used by the Settings UI.
