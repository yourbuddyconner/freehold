Governance

Freehold governs writes with declared policy rules and signed decisions. Every saved write is a changeset in the graph, and every approval or rejection is a decision record signed with your key. The rules decide what saves instantly and what waits for you.

The governance model

The central idea: a pending write is the system working correctly, not an error. When an agent writes something important, such as a preference about you or a new entity type, Freehold turns the write into a proposal instead of saving it silently. You review it and decide, and your decision is signed.

The agent is not blocked. It receives a well-formed response ({ status: "pending", proposal, rule }) and can keep working. The write is stored, not lost, and the agent can call pending_approvals to check on it later.

The policy rules in force are declared in the graph. You can read them in the Policy page of the console and, when a rule needs to change, edit it. That edit is itself a governed change that goes through your Inbox.

Write lifecycle

Every write follows the same path from agent call to verified record:

scratch
The agent writes a scratch note or another scratch-classified entity. The scratch-is-free rule matches it and it saves instantly.
pending
The agent writes something the rules cover, such as a preference or a schema change. The write becomes a pending proposal and the agent receives { status: "pending", proposal, rule }.
approved
You review the proposal in the Inbox — the agent's identity, its stated intent, the diff, and the rule that stopped it — and approve. The approval signs a decision record with your key.
indexed
Once a write is saved (instantly or after approval), Freehold folds the new objects into the PGlite index: one row per object plus a locally computed embedding. The index is derived data and can be rebuilt from the log.
recalled
The write is now searchable via recall. Every result carries its changeset hash, author, approval status, and the decision record if one exists.
verified
The Rust allod verify command passes on the graph. Three-level verification checks integrity (hash chain), authorship (signatures), and governance (decision records). The Verify page in the console shows per-changeset results.

Scratch writes

Scratch writes save instantly. The scratch-is-free rule, installed on every new graph, saves agent writes classified under workspace/scratch without review. Scratch writes are:

  • Entities created with remember, which are always scratch-classified
  • Entities and edges explicitly classified under workspace/scratch

Scratch exists so agents can work at full speed without every step requiring approval. Scratch notes are searchable, versioned, and carry their author and changeset like everything else. They just never need approval.

To promote a scratch note, an agent creates a governed entity that derives from it. That promotion needs your approval.

Pending writes

A write becomes pending when the policy rules say it needs your approval before it can be saved. The write is stored as a proposal. It is not lost, and the agent is not blocked.

The Inbox in the console shows each pending proposal with:

  • Agent identity — which registered agent made the write
  • Stated intent — the intent the agent declared in its call
  • Plain-language summary — what the write would do in ordinary terms
  • The diff — added attributes in green, changed in amber, presented in YAML shape
  • The rule that stopped it — which policy rule made the write pending, and its exact selector

You approve or reject, and either way the outcome is a signed record.

Decision records

Every approval and every rejection produces a decision record, signed with your key and stored as a changeset in the graph. The decision record contains:

  • The proposal being decided on (referenced by changeset hash)
  • The outcome — approved or rejected
  • Your key fingerprint and the signature
  • A timestamp

Decision records are auditable independently of Freehold. The Rust allod verify command checks that every governed write in the graph has a corresponding signed decision record. This is the third level of verification.

Rejection records are stored alongside approval records. A rejected write is not deleted from the graph: the proposal and its rejection are both part of the permanent record. This lets you audit what an agent attempted, not just what was saved.

Policy rules

Policy rules are declared in the graph and loaded on daemon start. Each rule has:

  • A plain-language title — what the rule does in ordinary terms
  • A selector — which writes the rule matches (entity types, taxonomy terms, attribute patterns)
  • Requirements — what the write must satisfy to save without approval, or the condition that makes it pending
  • Recent applications — which writes the rule stopped or let through, viewable in the Policy page

The rules installed with a new graph include:

  • scratch-is-free — agent writes classified as scratch save instantly
  • agent-writes-are-proposals — any non-scratch agent write waits for your approval
  • preferences-are-owner-business — a memory/Preference becomes true only with your signature
  • model-assisted-needs-signed-envelope — model-assisted writes must carry a signed attestation envelope
  • schema-changes-are-serious — schema changes wait for your approval

Editing a policy rule is itself a governed change. The console's Policy editor opens a YAML draft. Submitting it creates a proposal and sends it to the Inbox, where you approve your own change through the same flow agents use.

Schema changes

Schema changes ride the same lifecycle as knowledge writes. When an agent calls propose_ontology_change, Freehold creates a pending changeset that adds a meta/EntityType, meta/EdgeType, or meta/TaxonomyTerm node to the graph. The proposal appears in the Inbox with a preview of what the type would look like in the Schema viewer.

On approval, the type is installed in the graph's schema and becomes available for use in subsequent writes. The Schema viewer shows every agent-proposed type with its history: which agent proposed it, the changeset hash, and your signature on the approval. Pending schema proposals appear inline in the Schema viewer in amber, where they would land if approved.

Schema changes cannot be made silently. Policy requirements are conjunctive: when several rules match a write, all of their requirements apply, so no other rule can loosen what schema-changes-are-serious demands. Removing the rule is a policy change, which is itself governed.

Status vocabulary

Every object and changeset in the graph carries one of these statuses. The console uses the same vocabulary in the Inbox, the Memory browser, the Schema viewer, and the Verify page.

Status Meaning
scratch Saves instantly; never needs approval. The agent's working memory.
pending Submitted and waiting for your decision. The write is stored as a proposal; the agent received a valid response.
approved You approved it. The decision record is signed, and the write is saved and indexed.
rejected You rejected it. The signed rejection is stored and the write is not saved; the proposal remains auditable.
verified Hash chain, authorship signatures, and governance decision records all pass the three-level verification.
degraded Verification found an issue: a missing decision record, a signature that does not match, or a hash inconsistency. The Verify page shows the reason and a link to the affected object.
