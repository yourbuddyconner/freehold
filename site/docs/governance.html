Governance

Freehold decides what to do with each write by matching it against policy rules declared in the graph. Notes save immediately. Preferences, schema changes, and other writes the rules name go to your inbox, and your approval or rejection is signed with your key.

How writes are decided

Policy rules match writes by entity type and classification. A write that only touches scratch — the agent's working notes — saves as soon as it arrives. A write the rules name, such as a memory/Preference or a new entity type, is stored as a proposal instead. The response tells the agent the proposal's hash and which rule matched, and the agent can look the proposal up later with pending_approvals.

You decide proposals in the console's Inbox or with freehold approve and freehold reject. Either decision writes a record signed with your key into the same log as the memory itself.

The rules themselves are objects in the graph. The Policy page of the console lists them, and editing one creates a proposal that goes through your own inbox.

Write lifecycle

scratch
A write classified under workspace/scratch matches the scratch-is-free rule and saves immediately.
pending
A write the rules name — a preference, a schema change — is stored as a proposal. The response carries the proposal hash and the matched rule.
approved
You approve the proposal in the Inbox. The approval writes a decision record signed with your key, and the write saves.
indexed
Saved objects are folded into the search index: one row per object plus a locally computed embedding. The index is derived from the log and can be rebuilt from it.
recalled
recall returns the object with its changeset hash, author, approval status, and decision record.
verified
allod verify checks the hash chain, the signatures, and the decision records. The Verify page in the console shows per-changeset results.

Scratch writes

Scratch is the agent's working space. The scratch-is-free rule, installed on every new graph, saves writes classified under workspace/scratch without review:

  • Entities created with remember, which are always scratch-classified
  • Entities and edges explicitly classified under workspace/scratch

Scratch notes are searchable and versioned, and carry their author and changeset like every other object.

An agent promotes a scratch note by creating a governed entity that derives from it. The promotion goes through the rules like any other write.

Pending writes

A pending write is stored as a proposal in the graph. The Inbox shows each one with:

  • Agent identity — which registered agent made the write
  • Stated intent — the intent the agent declared in its call
  • Plain-language summary — what the write would do in ordinary terms
  • The diff — added attributes in green, changed in amber, presented in YAML shape
  • The matched rule — which policy rule made the write pending, and its selector

Approving saves the write. Rejecting stores a signed rejection. The proposal stays in the log either way.

Decision records

Every approval and every rejection produces a decision record, signed with your key and stored as a changeset in the graph. The decision record contains:

  • The proposal being decided on (referenced by changeset hash)
  • The outcome — approved or rejected
  • Your key fingerprint and the signature
  • A timestamp

The Rust allod verify command checks that every write which needed approval has a matching signed decision record, without running Freehold. Rejected proposals stay in the log with their rejection records, so the record shows every write an agent attempted.

Policy rules

Policy rules are declared in the graph and loaded when Freehold starts. Each rule has:

  • A plain-language title — what the rule does in ordinary terms
  • A selector — which writes the rule matches (entity types, taxonomy terms, attribute patterns)
  • Requirements — what the write must satisfy to save without approval, or the condition that makes it pending
  • Recent applications — which writes the rule matched, viewable in the Policy page

The rules installed with a new graph:

  • scratch-is-free — agent writes classified as scratch save immediately
  • agent-writes-are-proposals — any non-scratch agent write goes to your inbox
  • preferences-are-owner-business — a memory/Preference becomes true only with your signature
  • model-assisted-needs-signed-envelope — model-assisted writes must carry a signed attestation envelope
  • schema-changes-are-serious — schema changes go to your inbox

Editing a rule is itself a governed change. The console's Policy editor opens a YAML draft; submitting it creates a proposal, and you approve your own change through the same flow.

Schema changes

Schema changes follow the same lifecycle as knowledge writes. When an agent calls propose_ontology_change, Freehold creates a pending changeset that adds a meta/EntityType, meta/EdgeType, or meta/TaxonomyTerm node to the graph. The proposal appears in the Inbox with a preview of what the type would look like in the Schema viewer.

On approval, the type is installed and available for use in later writes. The Schema viewer shows each agent-proposed type with the agent that proposed it, the changeset hash, and your signature on the approval. Pending schema proposals appear inline in the viewer in amber, where they would land if approved.

Policy requirements are conjunctive: when several rules match a write, all of their requirements apply, so no rule can loosen what schema-changes-are-serious demands. Removing that rule is a policy change, which is itself governed.

Status vocabulary

Every object and changeset in the graph carries one of these statuses. The console uses the same vocabulary in the Inbox, the Memory browser, the Schema viewer, and the Verify page.

Status Meaning
scratch Saved immediately under the scratch rule. The agent's working notes.
pending Stored as a proposal, waiting for your decision.
approved Approved by you. The decision record is signed, and the write is saved and indexed.
rejected Rejected by you. The signed rejection is stored, the write is not saved, and the proposal stays in the log.
verified Hash chain, authorship signatures, and decision records all pass the three-level verification.
degraded Verification found an issue: a missing decision record, a signature that does not match, or a hash inconsistency. The Verify page shows the reason and a link to the affected object.
