Governance

Freehold's governance model is not an access control list. It is a record of decisions. Every admitted write produces a changeset in the graph. Every approved proposal produces a signed decision record. Policy rules determine what is admitted immediately and what requires your approval. The record is always auditable, regardless of the outcome.

The governance model

The central principle: a held write is the system working correctly, not an error. When an agent writes something consequential — a preference about you, a new type, a fact that will influence future behavior — the system holds it rather than admitting it silently. You review it, decide, and the decision is signed.

This is distinct from an approval gate that blocks the agent. The agent receives a well-formed response ({ status: "held", proposal, rule }) and can continue working. The write is queued, not lost. The agent can call pending_approvals to check its status.

The policy rules in force are declared in the graph. The owner can read them in the Policy page of the console and, when a rule needs to change, edit it — that edit is itself a governed change that routes through the Inbox.

Write lifecycle

Every write follows the same path from agent call to verified record:

scratch
The agent writes a scratch note or other scratch-classified entity. The admission layer classifies it as scratch and bypasses the policy engine.
held
The agent writes a governed entity — a preference, a person, a schema change. The policy engine matches the write against installed rules and holds it as a proposal. The agent receives { status: "held", proposal, rule }.
approved
The owner reviews the proposal in the Inbox: agent identity, stated intent, diff, and the rule that held it. The owner approves. The approval signs a decision record with the owner's key.
indexed
On admission (whether immediate or after approval), the core layer folds the new objects into the PGlite index: one row per object plus a locally-computed embedding. The index is derived data — it can be rebuilt from the log.
recalled
The write is now searchable via recall. Every result carries its provenance: changeset hash, author DID, approval status, and the decision record if approval was required.
verified
The Rust allod verify command passes on the graph. Three-level verification checks integrity (hash chain), authorship (signatures), and governance (decision records). The Verify page in the console shows per-changeset results.

Scratch writes

Scratch writes are admitted immediately and bypass the policy engine. The scratch-is-free rule is installed by default on every new graph. Scratch writes are:

  • Any write to the scratch region of the graph
  • Entities created with remember (always scratch-classified)
  • Entities explicitly classified under scratch in the taxonomy

Scratch is where agents think. It exists so agents can operate at full speed — capturing observations, building intermediate conclusions — without every step requiring approval. Scratch notes are searchable, provenance-carrying, and versioned; they are just not subject to governance approval.

An agent can promote a scratch note to governed memory by creating a governed entity that derives from it — that promotion is held by policy.

Held writes

A write is held when the admission layer, after running it through the policy engine, determines that it requires owner approval before it can be admitted to the graph. The write is stored as a proposal — it is not lost, and the agent is not blocked.

The Inbox in the console shows each pending proposal with:

  • Agent identity — which registered agent made the write
  • Stated intent — the intent the agent declared in its call
  • Plain-language summary — what the write would do in ordinary terms
  • The diff — added attributes in green, changed in amber, presented in YAML shape
  • The rule that held it — which policy rule triggered the hold and its exact selector

The owner approves or rejects. Both outcomes produce a signed record.

Decision records

Every approval and every rejection produces a decision record, signed with the owner's key and stored as a changeset in the graph. The decision record contains:

  • The proposal being decided on (referenced by changeset hash)
  • The outcome — approved or rejected
  • The owner's key fingerprint and the signature
  • A timestamp

Decision records are auditable independently of Freehold. The Rust allod verify command checks that every governed write in the graph has a corresponding signed decision record. This is the third level of the trust loop.

Rejection records are stored alongside approval records. A rejected write is not deleted from the graph — the proposal and its rejection are both part of the permanent record. This lets you audit what an agent attempted, not just what was admitted.

Policy rules

Policy rules are declared in the graph and loaded on daemon start. Each rule has:

  • A plain-language title — what the rule does in ordinary terms
  • A selector — which writes the rule matches (entity types, taxonomy terms, attribute patterns)
  • Requirements — what the write must satisfy to be admitted without a hold, or the hold condition
  • Recent applications — which writes the rule held or admitted, viewable in the Policy page

The default rules installed with a new graph include:

  • scratch-is-free — writes classified as scratch are admitted immediately
  • preferences-require-approval — any write creating or modifying a memory/Preference is held
  • schema-changes-are-serious — all propose_ontology_change calls are always held

Editing a policy rule is itself a governed change. The console's Policy editor opens a YAML draft; submitting it creates a proposal and routes it to the Inbox. The owner approves their own change — the loop made visible.

Schema governance

Schema changes ride the same lifecycle as knowledge writes. When an agent calls propose_ontology_change, the system creates a held changeset that adds a meta/EntityType, meta/EdgeType, or meta/TaxonomyTerm node to the graph. The proposal appears in the Inbox with a preview of what the type would look like in the Schema viewer.

On approval, the type is installed in the graph's schema and becomes available for use in subsequent writes. The Schema viewer shows every agent-proposed type with its provenance — which agent proposed it, the changeset hash, and your signature on the approval. Schema proposals that are held appear inline in the Schema viewer in amber, where they would land if approved.

Schema changes cannot be made silently. The schema-changes-are-serious rule is unconditional — it cannot be overridden by another rule, and it cannot be removed without itself going through the governance loop.

Status vocabulary

Every object and changeset in the graph carries one of these statuses. The console uses the same vocabulary everywhere — in the Inbox, Memory browser, Schema viewer, and Verify page.

Status Meaning
scratch Admitted immediately; not subject to governance approval. The agent's working memory.
held Submitted, awaiting owner approval. The write is stored as a proposal; the agent received a valid response.
approved Owner approved; decision record signed; write admitted to the graph and indexed.
rejected Owner rejected; signed rejection record stored; write not admitted. The proposal remains auditable.
verified Hash chain, authorship signatures, and governance decision records all pass the three-level verification.
degraded Verification found an issue: a missing decision record, a signature that does not match, or a hash inconsistency. The Verify page shows the reason and a link to the affected object.
