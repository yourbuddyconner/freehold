Your agents' memory,
in a graph you own.

Most memory products lease you back your own data. Freehold keeps your agents' accumulated knowledge in an Allod graph: an append-only log of signed changes, verifiable from your keys alone, governed by rules you declare. It runs on your machine, your agents connect over MCP, and nothing consequential becomes memory without your approval.

The founding loops

Three loops: memory, schema, and trust

Everything Freehold does falls into one of three loops, and each ends in a signed record you can verify.

01 — MEMORY LOOP

Write, hold, approve, recall

Scratch notes are admitted immediately, so agents can think at full speed. Consequential writes are held as proposals: a preference about you, an entity outside the scratch region. You approve in the Inbox, and the approval is a signed decision record. Recall returns every result with its provenance: who wrote it, who approved it, the changeset hash.

How governance works
02 — SCHEMA LOOP

The agent can extend its own schema

Memory is a typed knowledge graph, not a pile of notes. Entities have types, relationships are typed edges, and the schema lives in the graph itself. An agent reads the schema with describe_schema and, when the graph lacks a type it needs, proposes one with propose_ontology_change. Schema changes are always held, reviewed in the same Inbox as everything else, and installed when you approve them.

Schema tools reference
03 — TRUST LOOP

Verify without trusting Freehold

The Rust reference implementation's allod verify passes on graphs Freehold writes, so verification never depends on trusting Freehold. The PGlite search index is derived data: freehold reindex rebuilds it from the log and must land on identical state.

MCP tool surface

Twelve tools, grouped by function

Agents connect over streamable HTTP MCP at /mcp. There are no tools for approving, rejecting, or changing policy. Those actions belong to you.

Knowledge
remember
Fast path for a scratch note. Creates a memory/Note and admits it immediately. Sugar over create_entity.
Knowledge
create_entity
Create a typed node with optional classifications and edges in one atomic changeset. The type is any entity type installed in the graph.
Knowledge
update_entity
Revise an existing entity's attributes with optimistic concurrency against the entity's current revision.
Knowledge
relate
Create a typed edge between two nodes. Time lives on edges (from/until), per the corp-ontology convention.
Knowledge
classify
Place a node, edge, or document in the taxonomy. Classification routes policy, so this write can be held.
Knowledge
attach_document
Anchor source material by content hash, so claims can cite exact bytes. Returns the document's content-hash address.
Retrieval
recall
Hybrid semantic + full-text search over the PGlite index. Filters by type, region, author, approval status. Every result carries provenance.
Retrieval
get_entity
One object in full: attributes, classifications, edges, provenance chain, and revision history.
Retrieval
traverse
Walk the typed graph from a starting node: follow edge types in either direction, up to a configurable depth.
Retrieval
pending_approvals
The agent's view of its own held writes — proposals awaiting owner approval.
Schema
describe_schema
Return the graph's installed ontologies as data: entity types, edge types, the taxonomy tree, versions, and import hashes.
Schema
propose_ontology_change
Propose a new entity type, edge type, or taxonomy term. Always held — reviewed in the owner's inbox, installed on approval.
Governed write

From write to signed record

A held write is the system working correctly, not an error. Here is what happens to a consequential write, start to finish.

Step 01

Agent writes

Agent calls create_entity with type memory/Preference. The request reaches the admission layer.

scratch → immediate
Step 02

Policy holds the write

The policy engine matches the write against the installed rules. A preference about the owner needs the owner's approval, so the write is held and the agent receives { status: "held", proposal, rule }.

held
Step 03

Owner reviews and approves

The proposal appears in the Inbox: agent identity, stated intent, plain-language summary, the object diff, and the rule that held it. The owner approves.

approved
Step 04

Decision record signed

Approval signs a decision record with the owner's key. The write is admitted, indexed, and returned by recall with its provenance: changeset hash, author, approval signature.

verified
Quickstart

Up in four commands

Prerequisites: Node ≥ 22, pnpm, and Rust with wasm-pack (for the one-time Allod WASM build). Both repos must be siblings on disk.

bash 
# 1. Clone both repos as siblings
git clone https://github.com/yourbuddyconner/allod
git clone https://github.com/yourbuddyconner/freehold

# 2. Build the Allod wasm package (one time)
cd allod/crates/allod-wasm && pnpm install && pnpm build && cd ../../..

# 3. Install dependencies and start the daemon
cd freehold && pnpm install
pnpm --dir packages/api exec tsx src/cli/index.ts serve
# Binds 127.0.0.1:8710 — console at http://127.0.0.1:8710

# 4. Wire an agent
freehold mcp setup claude-code   # writes the MCP config entry
freehold mcp setup --print        # or print JSON for any other agent
