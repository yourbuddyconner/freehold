# Review hardening: onboarding, lifecycle, GitHub bridge

Six changes from the 2026-08-06 adversarial audit. Each is independently
shippable; together they take the review system from single-operator demo
to something a small team can adopt.

## Global decisions

- The Rust `allod` binary stays the canonical implementation of graph init
  and commit indexing. The daemon learns where it is: `allodBin` in
  `~/.freehold/config.json` (default: `allod` resolved on PATH). Every
  shell-out validates the binary exists first and surfaces a plain error
  naming the config key when it does not.
- Signing keys are generated by freehold natively (node `crypto`
  Ed25519), written as plain-keypair YAML (`name`, `key_id` = plain
  SHA-256 of the raw 32-byte public key rendered `sha256:<hex>`,
  `algorithm: ed25519`, `public`, `secret` hex) to
  `$ALLOD_KEYS_DIR || $XDG_DATA_HOME/allod/keys || ~/.local/share/allod/keys`
  `/<graph-dir-component>/<principal>.yaml`, `0600` in `0700` dirs.
  Never overwrite an existing key file.
- All signed graph writes continue through the two-phase `signedCommit`
  helper. No new signing paths.

## 1. Repo onboarding — `freehold repo add` + Settings UI

CLI: `freehold repo add <path> [--name <n>] [--id <id>] [--principal <p>]
[--no-index]`. Steps, each printed as it runs, idempotent where possible:

1. If `<path>/.allod/graph.yaml` is absent, run
   `allodBin graph init <path> --owner <principal>` (verify the actual
   init subcommand from `allod --help` at implementation time; if the
   binary is missing, stop with the config-key error).
2. Generate the principal's key if absent (native, above).
3. `POST /graphs` (via the daemon HTTP API with the local token — the CLI
   already talks to the daemon this way) with path, name, id,
   signingPrincipal; the existing registerRepo handles review-ontology
   install, originRemote, first syncIndex.
4. Unless `--no-index`: `allodBin git index <path> <default-branch> --as
   <principal>`.
5. Print a summary: graph id, principal, key location, next steps
   (connector setup pointer).

Web: Settings gains a "Repositories" section with an Add form (path,
name, principal — default `owner`), calling a new
`POST /repos/onboard` endpoint that performs the same steps server-side
(the daemon has filesystem access; the UI cannot run CLIs). Progress
reported as a step list in the response; failures return the step that
failed and its error. The graph dropdown picks up the new graph on the
next `useListGraphs` invalidation.

## 2. Reviews with verdicts also decide

`postReview` gains `decide?: boolean` (default true). When true and the
proposal is currently undecided: verdict `approve` /
`approve-with-comments` → `decideGit(..., "approve")`;
`request-changes` → `decideGit(..., "reject")`, after the artifacts
commit, same error surfacing as the decide route (including
`pushed`/`pushError` passthrough in the response). If a decision already
exists, skip the decide and return `alreadyDecided: true`.
The review page stops calling decide separately (single `postReview`
call); the card's ReviewComposer inherits the fix with no UI change.

## 3. Auto-index on evaluation

When `evaluateSha` finds any touched path unindexed, the daemon fires a
background `allodBin git index <repoDir> <sha> --as <signingPrincipal>`
(one in-flight per repo, dedup by sha, log-only failures) and evicts that
sha's cache entry on completion so the next fetch shows indexed chips.
The "not yet indexed" caption becomes "Indexing." while a run is in
flight for that sha. If `allodBin` is unavailable, behavior is unchanged
(caption keeps the CLI hint).

## 4. Branch scoping

`GraphEntry` gains `ignoreBranches: string[]` (glob patterns matched
against the branch name without `refs/heads/`, default `[]`).
`listGitProposals` filters `branchHeads` through it. PATCH `/graphs/:id`
accepts it; Settings shows a per-repo-graph editable pattern list with
placeholder text suggesting `worktree-*`. OpenAPI + client regen.

## 5. Outbound GitHub commit status on decide

After a successful decide on a repo graph with a configured GitHub
connector, the daemon posts a commit status to the origin repo
(`POST /repos/{owner}/{repo}/statuses/{sha}`): context
`freehold/review`, state `success` for approve / `failure` for reject,
description `approved by <principal>` / `changes requested by
<principal>`, target_url pointing at the local review page. Works with
both credential-mode PATs and App installation tokens (reuse the existing
token plumbing in the connector). Fire-and-forget with the result
recorded in the decide response as `statusPosted: boolean` and a subdued
notice in the UI on failure. Owner/repo parsed from `originRemote`
(https and ssh forms).

## 6a. Force-push carry-forward (same-tree heuristic)

`evaluateSha` computes the commit's tree hash. If any decision in the
notes covers a commit whose tree hash matches, the proposal carries
`priorDecision: { sha, verdict, decidedBy, decidedAt }`. UI: a chip on
the card and review page — "same content approved as <short-sha>" — and
the approve button relabels "Approve again". No automatic decisions:
the heuristic informs, the human decides. Tree hashes of decided commits
are resolved lazily and cached with the proposal cache (decided shas may
be unreachable after force-push — treat resolution failure as no match).

## 6b. Second-principal onboarding

CLI: `freehold principal add <name> [--graph <id>] [--role <role>]` —
generates the key (native), registers the principal in the graph (use
whatever principal-registration operation the graph exposes — read how
graph init registers the owner; if registration requires a policy-roles
change, stage a policy proposal via the new install_policy_ops path and
say so in the output). Settings' Principals section gains the same via a
small form. Out of scope: remote key distribution — the command prints
the key path and a one-line "copy this file to the reviewer's machine
under the same path" instruction.

## 6c. Apply suggestion as a commit

`POST /git/proposals/:sha/suggestions/apply` with `{ path, span, body:
suggestionText, by, branch }`: the daemon builds a commit on
`refs/heads/<branch>` using pure git plumbing — read the blob at the
branch tip, splice the span's lines with the suggestion, `hash-object` /
`mktree` / `commit-tree` (author = `<by> via freehold`), `update-ref`
with an old-value guard so a concurrent push fails cleanly (409
`branch-moved`). No working-tree mutation. Only additions-side spans on
text files; 422 otherwise. UI: saved suggestion cards gain "Apply as
commit" next to Copy; on success, invalidate proposals (the new tip
appears as a proposal, softened by 6a's carry-forward chip). The commit
does NOT auto-decide.

## Testing

Every item: unit tests at the layer it changes plus the established
route/component test patterns. Items 1 and 6b get CLI-level tests with a
fake daemon; item 6c gets plumbing tests against a fixture repo
(`git init -b main`) covering the old-value guard race. Live verification
on the allod graph before each merge where feasible (onboard a scratch
repo end to end; apply a suggestion on a demo branch).
